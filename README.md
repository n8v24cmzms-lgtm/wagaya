# わが家の食材手帳（Web配布版）

冷蔵庫の在庫と賞味期限を管理し、**フレンドコードで同じ冷蔵庫を家族と共有**できる Web アプリです。
スマホのホーム画面に追加すればアプリのように使えます（PWA）。利用は無料、データは Firebase の無料プラン（Spark）に保存します。

> **2026-11-09 バックエンド移行**: データの置き場所を Supabase から **Firebase**（Authentication / Firestore / Storage / Hosting）に作り替えました。画面・機能・デモモードはそのままです。旧 Supabase 実装（`js/supabase-store.js`、`supabase/schema.sql`）はロールバック用に残してあります（`config.js` に旧設定が両方入っている場合のみ旧経路で動きます）。

- 見た目：ベージュ系ナチュラル、常に明るい背景（ダークモードなし）
- ビルド不要：このフォルダをそのまま静的ホスティングに置けば動きます
- 設定なしで開くと **デモモード**（その端末の中だけ）で全機能を試せます
- **アプリの狙い**：家族みんなで楽しく買い物すること。大人だけでなく、子どものおつかいの手助けにもなること。食材図鑑を集める楽しさ（激レア食材・レベル・食育コンテンツ）で、子どもが買い物に行きたくなる仕掛けを入れています

## 機能

- 在庫管理：期限で自動グループ分け（すぐ使いたい／今週中に／まだ余裕あり）、数量 ±、写真添付（任意）
- **分数単位**：白菜・キャベツなど「玉」単位の食材は、半玉（1/2）・1/4玉・3/4玉のような分数で登録・表示・増減できます。登録フォームで単位を「玉」にすると分数のクイック選択が出て、数量ボタンは 1/4 玉刻みになります（他の単位は従来通り）。残りわずか判定や買い物リストでも分数のまま扱えます
- お知らせ：期限が近い・お気に入りが残りわずか
- お気に入り食材：少なくなると買い物リストへ自動追加
- 買い物リスト：「買った！」で在庫に戻る
- レシピ：「あるもので作る」（買い足しなし）／「買い出しで作る」（足りない材料を買い物リストへ）。分量は家族人数で換算
- **レシピお気に入り**：レシピカードの ☆ で保存でき、レシピ画面の「★ お気に入り」から見返せます。レシピは在庫から都度生成されるため、保存時は内容（名前・材料・分量・手順）をスナップショットとして残します。お気に入りはユーザーごとに保存され、同じ冷蔵庫の他のメンバーには見えません（本番は Firestore の `favorite_recipes`＋本人のみ許可のルール、デモは端末内保存）
- **食材アイコン**：各食材に一目でわかるSVGアイコンを同梱（`js/icons.js`、個別アイコン119種＋カテゴリ汎用10種）。在庫カード・買い物リスト・登録フォームのプレビュー・レシピ材料に表示。食材名から自動で引き、未知の食材はカテゴリ汎用アイコンにフォールバック
- **アイコンのかわいい刷新（2026-11-07）**：線を太めの温かいブラウンにし、全アイコンに柔らかい落影を追加。食材色を少し鮮やかに寄せ（原色は使わない）、果物・野菜など一部に金色のキラキラ、豆腐・卵・ごはん・かぶに薄いほっぺのアクセントを付けた。在庫カードのアイコンタイルは丸みを強めたグラデーション＋影付きに、図鑑のアイコンは丸いスポット背景に変更（未登録のグレースケール表示は維持）。sw キャッシュは v4
- **アイコンに顔を追加（2026-11-07）**：個別83種＋カテゴリ汎用10種の全アイコンに、共通画風の顔（丸い点目＋小さな笑口＋薄ピンクのほっぺ）を付けた。顔の位置・大きさはアイコンごとに調整し、食材の特徴（葉・尾・切り口など）を隠さないよう配置。瓶ものはラベル／胴、楕円・筒状のものは形に合わせて傾けた。元々目玉ドットがあった魚・カニ・イカは顔と二重にならないようドットを除去。図鑑の未登録表示では顔も含めてグレースケールになる。sw キャッシュは v5
- **アイコンを絵本風に刷新＋表情で個性付け（2026-11-08）**：ユーザーが見本に挙げた絵本風イラスト（冷蔵庫イラスト内の食材たち）に寄せ、輪郭を細めの温かいブラウン（#9e744a・線幅1.35）に、塗りを淡いパステルの水彩風（彩度の高い色55色を置換）へ変更し、落影も薄くした。顔は全員同じをやめ、食材ごとに表情を固定で割り当てた（`EXPR`）：にっこり（にんじん・牛乳・りんご等15種）／^^＋開いた口（キャベツ・ピーマン・いちご等13種）／おだやか（大根・魚・お茶等13種）／ねむい（卵・ブロッコリー・レモン等11種）／大きな口＋舌チラリ（トマト・とうもろこし・餃子等10種）／舌ペロ（きゅうり・チーズ・バナナ等9種）／照れ・濃いほっぺ（白菜・豆腐・桃等9種）／びっくり・oの口（玉ねぎ・イカ・キウイ等7種）／ウインク（ねぎ・なす・納豆等6種）。ほっぺの濃さも表情ごとに変えている。顔の位置・大きさ・傾きは従来通り食材の特徴を隠さない配置。図鑑の未登録表示では顔も含めてグレースケールのまま。sw キャッシュは v6
- **アイコンの仕上げ直し（2026-11-08）**：「イラストが雑すぎる」との指摘を受け、全93種（個別83種＋カテゴリ汎用10種）の形を描き直した。形は左右対称・重心中央を基本に円/楕円/丸角矩形など整った形で再構成し、白菜の葉脈・キャベツの層線・枝豆の豆・ぶどうの粒・メロンの網目・れんこんの穴などの細部を等間隔/対称に配置。浮いて見えた線（大根の根線が顔を横切る等）や重なって潰れた部分（えのきの傘、もやしの頭、納豆の豆と糸の絡み）を解消し、顔の位置も形に合わせて中央へ寄せ直した。線幅（1.35）と角の丸み、顔の比率は全アイコンで統一。表情（`EXPR`）の割り当てと淡パステルの色は従来通り。検証は全アイコンのコンタクトシートをレンダリングして目視確認（大サイズ＋36px相当）し、気になった8種＋3種を個別に拡大して直した。sw キャッシュは v7
- **アイコンを「キャラクター」化（2026-11-09）**：「アイコンっていうよりキャッチーなキャラクターのイメージ」という方向転換を受け、全93種をピクトグラム＋顔から「食材キャラ」に仕上げ直した。食材の形そのものを体として、(1) 食材の特徴をキャラの特徴に見立てた小物（`CHAR_ACC`：卵の割れた殻＝帽子、牛乳/豆乳パックのストロー、魚介の泡、あさりの真珠、葉っぱ＝髪/帽子、ブロッコリーの房のドット、納豆の箸、豆腐の青ねぎ、ねぎ/アスパラの束バンド、ごはん/餃子/味噌の湯気、チョコのハート刻印など）、(2) 左上のツヤ（`GLOSS`、28種）でぷっくり感、(3) 表情タイプに合わせた体の傾き（`TILT`：元気な表情は±4〜5°、おだやか/ねむいは±2〜3°、びっくりは0°）と、元気な7種への小さなバウンス弧（`HOP`）で個性を出す。ユーザーの指定により手足は付けていない（「手足はなくていい」）。前回の仕上げ直しの整った形・淡パステル・細い温かブラウン線・表情割り当て（`EXPR`）はそのまま。図鑑の未登録表示ではキャラ全体がグレースケールになる。検証は全93種のコンタクトシート（大サイズ＋40px）目視確認とデモフローテスト全62項目パス。sw キャッシュは v8
- **イラストの使い回し解消（2026-11-09）**：「同じイラストは使いまわさない」という指示を受け、図鑑カタログ全116種が必ず自分専用のキャラに解決されるよう監査・分離した。修正前は15キー・延べ47品目が同一イラストを共有していた（魚8種が全部 `fish`、きのこ5種が全部 `mushroom`、麺5種が全部 `noodles`、豆腐系4種、葉物4種（ほうれん草に小松菜・ズッキーニ・大葉）、豚肉3種、鶏肉2種、ハム/ベーコン、イカ/タコ、あさり/ほたて、米/餅、食パン/ロールパン、塩・砂糖・ツナ缶、サラダ油/ごま油）。新規専用キャラ36種を追加（個別アイコンは計119種）：きのこ類は品種ごとに完全分離（しいたけ=ひび割れ傘、えのき=細い束、しめじ=株束、舞茸=フリル、エリンギ=太い軸、マッシュルーム=白い丸傘）。あわせて「片栗粉」が「栗」を含むため栗アイコンに誤解決される問題も修正。色だけ変えたコピーも使い回しとみなし、豚/牛/カテゴリ肉、牛乳/豆乳/カテゴリ乳製品、豆腐/カテゴリ大豆、魚/カテゴリ魚、カップ飲料/カテゴリ飲料、りんご/カテゴリ果物、醤油瓶/油瓶、お茶/コーヒーの土台アートも描き分けた。カテゴリ汎用キャラはカタログに無い未知・自由入力の食材名専用に限定。検証はプログラム監査（カタログ116種→キー・最終SVGハッシュ・色/傾き正規化ハッシュすべて重複ゼロ、全129キーの色違いコピーもゼロ）、コンタクトシート目視（カタログ名前付き・大サイズ・44px）、デモフローテスト全66項目パス（使い回し禁止のアサーションを追加）。sw キャッシュは v9
- **食材図鑑**：下部バーの「図鑑」タブ。定番食材116種をカテゴリ別グリッドで表示し、在庫に登録した食材が自動でコレクションされる（登録済みはカラー＋「登録済み」、未登録は薄く「まだ」表示、進捗バー付き）。セルをタップするとその食材が在庫登録フォームに入る。コレクションのスコープは**冷蔵庫単位**（家族全員で1つの図鑑を共有。在庫から消しても記録は残る。本番は Firestore の `fridge_catalog`＋メンバー限定ルール、デモは端末内保存）
- **激レア＆レア食材（2026-11-09）**：図鑑にレアリティを追加。激レア24種（松茸・トリュフ・キャビア・フォアグラ・あわび・伊勢海老・ふぐ・毛ガニ・タラバガニ・うに・本まぐろ・和牛・金目鯛・のどぐろ・花山椒・こしあぶら・たらの芽・ふきのとう・じゅんさい・夕張メロン・ルビーロマン・太陽のタマゴ・白いちご・デンスケすいか）とレア12種（いくら・からすみ・あん肝・さくらんぼ・シャインマスカット・マンゴー・ライチ・ズワイガニ・甘えび・うなぎ・ドラゴンフルーツ・生ハム）、全種に専用キャラ（使い回しなし・手足なし）。図鑑では金色の枠＋「激レア！」バッジで特別表示し、未収集のレアはシルエット風＋「❓ 未発見」でワクワク感を出す（未収集と分かる表示は維持）。ヘッダーに「激レア ○/24 ゲット」「レア ○/12 ゲット」の進捗と、レアリティ絞り込み（すべて／激レアだけ／レアだけ）。激レアを初めて登録するとお祝いトースト（「激レア食材『松茸』をゲット！🎉」）が出る（買い物リストの「買った！」経由でも発火）。レアリティはカタログ側の静的メタデータ（`js/icons.js` の `RARITY`）で、DBスキーマ変更なし。あわせて在庫キャラの「キラキラ」アクセントは、ユーザーの方針（キラキラ・キュルキュルした目は要らない）に合わせて廃止した
- **標準カタログの拡充（2026-11-09）**：「一般的にスーパーで売られているものは登録できること」を目標に監査し、62種を追加してカタログは全214種になった。野菜（チンゲン菜・水菜・春菊・豆苗・にら・長芋・みょうが・ゴーヤ・パプリカ・ミニトマト・絹さや・スナップエンドウ・そら豆・モロヘイヤ）、果物（オレンジ・グレープフルーツ・いちじく・びわ・ゆず・ブルーベリー）、肉（手羽元・豚ロース）、魚介（かつお・かれい・ほっけ・ししゃも・明太子・たらこ）、卵（うずら卵）、豆腐・練り物・漬物（かまぼこ・ちくわ・はんぺん・さつま揚げ・がんもどき・こんにゃく・しらたき・キムチ・梅干し・たくあん）、主食（フランスパン）、調味料・乾物（酢・みりん・料理酒・マヨネーズ・ケチャップ・ソース・ポン酢・コンソメ・鶏ガラスープ・だしの素・胡椒・わさび・春雨・わかめ・昆布・ひじき・サバ缶・コーン缶・トマト缶・パン粉）、冷凍（冷凍ポテト・ミックスベジタブル）。全種が専用キャラに解決される（パプリカ≠ピーマン、オレンジ≠みかん 等の混同も解消）。個別アイコンは計217種＋カテゴリ汎用10種
- **食材レベルと称号（2026-11-09）**：図鑑コレクションに「買った回数」を記録し（在庫登録と買い物「買った！」で+1。在庫から消しても回数は残る）、回数でレベルと称号が付く。ユーザーの指定で回数は大きめ： Lv1=1回、Lv2=5回、Lv3=10回、Lv4=20回、Lv5=35回、Lv6=50回、Lv7=75回、Lv8=100回、Lv9=150回、Lv10=200回、以降+100回ごと（最初のLv2だけ早めに届く）。称号は Lv1『○○ビギナー』、Lv2『○○ファン』、Lv3『○○はかせ』、Lv4『○○マスター』、Lv5『○○の達人』、Lv6『○○の匠』、Lv7『○○の賢者』、Lv8『伝説の○○』、Lv9『○○の覇王』、Lv10『○○の神さま』、Lv11〜『真・○○の神さま』。図鑑セルに Lv・回数・称号・「あと○回でLvアップ」を表示し、レベルアップ時はお祝いトースト（激レアゲットと同時の場合は激レアを優先）。本番は Firestore の `fridge_catalog.purchaseCount` フィールド（メンバーだけが増やせるようルールで制限）
- **レシピのバリエーション拡充（2026-11-09）**：「レシピはもう少しバリエーション出せた方が嬉しい」を受けて、レシピを全39品に増やした。同じ主材料でも調理法・味付けの違う料理を複数用意し（鶏肉なら親子丼／唐揚げ／塩焼き／蒸し鶏サラダ／トマト煮／油淋鶏／スープなど。和風・洋風・中華、炒める・煮る・焼く・蒸す・揚げる・スープ・サラダ）、各レシピにコース（主菜／副菜／汁物／主食）を持たせて「主菜＋副菜＋汁物」の**献立セット**も提案する（レシピ画面の「🍽 今日の献立セット」）。少量の残り食材を活かす**使い切りレシピ**（useUp）も追加。提案順には日替わりローテーション（`rotateKey`、既定は当日日付）を小さく効かせ、同じ顔ぶれが続かないようにした（期限の近い食材を優先するスコア差の方が大きいので FIFO の優先順位は崩れない）。2モード（あるもの／買い出し）・家族人数での分量換算は従来通り
- **レシピの消費順（2026-11-09）**：ユーザーの指定順「消費期限の近いもの → 先に買ったもの → 期限がまだなものの順」で食材を使うよう、`js/recipes.js` に消費順を実装。同一食材の複数ロットは (1)期限が近い順 (2)期限が同じなら購入（登録）が古い順 (3)期限なしは最後に購入順、で並べ替え（`compareLotsForUse`／`lotsForIngredient`）。レシピ提案のスコアも代表ロット（消費順の先頭）の期限の近さ・古さで加点し、期限間近の食材を使う料理が上に来る。使用量の割り当て計画 `planUsage` も同順。UIには「期限の近いものから使います」チップと、材料ごとの対象ロット（期限・購入日・在庫件数）を表示。なお現状アプリに「調理して在庫を減らす」フローはないため、減算そのものではなく「どのロットから使うか」の提案・計画として実装している

- **はじめてガイド**：初回にだけ「登録 → 買い物 → レシピ」＋フレンドコード／QRでの参加方法を3+1ステップで表示（家族・子ども向けの言葉）。閉じると端末内に「表示済み」を記録し、次回からは出ません。設定タブの「はじめてガイドを見る」からいつでも再表示できます（`js/guide.js`）

- **よく買うものからワンタップ登録**：登録フォーム上部に「よく買うもの」（図鑑の購入回数順）と「最近登録したもの」のチップを表示。タップで名前・カテゴリ・単位がフォームに入り、あとは「登録する」を押すだけです
- **通知**：設定タブで通知の許可をONにできます。今すぐ動くのは「アプリを開いたときのローカル通知」（期限3日以内・お気に入り残りわずかを1日1回まで、この端末に通知。サーバー不要）。アプリを開いていないときの通知（サーバー発プッシュ）は下記「プッシュ通知（サーバー発）について」の設定が済んでから有効になります

## プッシュ通知（サーバー発）について

通知には2種類あり、状態が違います。

| 種類 | 状態 | 必要なもの |
|---|---|---|
| ローカル通知（アプリを開いたとき） | ✅ 実装済み・今すぐ使える | 設定タブで通知許可をONにするだけ |
| サーバー発プッシュ（FCM／アプリを開いていないとき） | ⏳ クライアント側（トークン登録・SW受信）は準備済み。送信側の有効化が未完 | 下記の手順 |

準備済みのもの:

- FCM トークン登録: `FirebaseStore.registerPushToken()` が `users/{uid}/push_tokens` にトークンを保存（本人のみ読み書き可のルール）。`config.js` の `FCM_VAPID_KEY`（Firebase コンソールで発行する Web Push 証明書キー）が空の間は登録を開始しない
- バックグラウンド受信: `sw.js` に FCM の `onBackgroundMessage` を同梱（Firebase 設定があるときだけ初期化）。標準構成用の `firebase-messaging-sw.js` も予備として同梱（同時登録はしないこと）
- 送信側の雛形: `firebase/functions/send-reminders.scaffold.js`（未実装の明示つきスケルトン）

**有効化に残っている作業（公開後でよい）**:

1. Firebase コンソール → プロジェクトの設定 → Cloud Messaging で Web Push 証明書キーを発行し、公開鍵を `config.js` の `FCM_VAPID_KEY` に入れる
2. 送信処理を実装する: Cloud Functions（**Blaze プラン＝カード登録が必要**）で定期実行し、`push_tokens` を読んで期限3日以内・残りわずかを集計し FCM 送信。無効トークンは削除する。雛形は `firebase/functions/send-reminders.scaffold.js`
3. Blaze を避けたい場合の代替: GitHub Actions の schedule 等の外部定期実行から、サービスアカウント鍵（CI の Secrets にだけ置く）で小さな送信スクリプトを1日1回動かす
4. 実機でトークン登録→送信→タップでアプリが開く、まで確認する

**サーバー発プッシュは現時点では動作しません**（届くのは開いたときのローカル通知のみ）。

## リアルタイム更新について

- 本番モード: `FirebaseStore.subscribeFridge()` が Firestore の `onSnapshot` で現在の冷蔵庫の `items` / `shopping_items` / `fridge_catalog` を購読します。ルールが適用されるため、メンバーでない人の変更が届くことはありません。追加の有効化設定は不要です
- デモモード: localStorage はタブ間で共有されるため、`storage` イベントで変更を検知して再読み込みします（同じブラウザの別タブ向け。別端末間では同期しません）
- 購読に失敗した場合は自動で従来動作（操作時・再読み込み時の反映）に戻ります

## セキュリティ設計（最優先事項）

- **Firestore セキュリティルール**（`firebase/firestore.rules`）：全コレクションで「冷蔵庫のメンバーだけが、その冷蔵庫のデータを読み書きできる」を強制。匿名アクセスは一切なし
- **管理者用の秘密鍵はフロントに置きません**。ブラウザが使うのは Web 公開設定（apiKey 等）のみで、これは秘密鍵ではありません（制御はルールが担います）
- **フレンドコード**：Firestore には SHA-256 ハッシュをドキュメントIDとする `fridge_codes/{ハッシュ}`（中身は fridgeId だけ）だけを置き、参加はハッシュで1件引くだけ。一覧・前方一致検索はルールで禁止。コードは推測しにくいランダム8文字です
- **コードの平文**は `fridge_invite_codes` に分離し、ルールで「冷蔵庫の作成者本人だけ」が読めます（メンバーにも見えません）
- **既知の制限（正直な注記）**：旧 Supabase 版にあった「コード参加の試行回数制限（10分で10回）」は、Firestore ルールだけでは実装できません（Cloud Functions = Blaze が必要）。緩和策として、長いランダムコード・再発行で旧コード即無効・fridgeId 自体も推測不能なランダムID、という設計にしています。本格運用で総当たり対策を強める場合は、参加処理を Cloud Functions 経由に移してください
- **パスワード**は Firebase Authentication が管理し、このアプリは保持しません
- **写真**は Firebase Storage の `fridges/{fridgeId}/items/` に保存し、ルールでメンバーだけが読み書きできます（画像のみ・5MB以下）。メンバーの判定は Firestore の所属ドキュメントで行います
- **レシピお気に入り**もルールで「本人のものだけ読み書き可」です（所属する冷蔵庫の範囲内。他のメンバーのお気に入りは見えません）
- **QR コード**は同梱ライブラリで端末内生成のみ。フレンドコードを外部の QR 生成 API に送ることはありません
- ユーザー入力の表示はすべて `textContent` 経由（XSS 対策）

## デプロイ手順

### 1. Firebase プロジェクトを作る

1. [Firebase コンソール](https://console.firebase.google.com) に **Google アカウント**でログインし、「プロジェクトを追加」で新規プロジェクトを作成（無料の Spark プランで OK。Google Analytics は任意）
2. **Authentication** → 始める → ログイン方法で **メール / パスワード** を有効化
   - 「メールリンク」等の他方式は不要です。メール確認メール自体は登録時にアプリから送信されます
3. **Firestore Database** → データベースを作成（本番モード、リージョンは `asia-northeast1`（東京）推奨）
4. Firestore の **ルール** タブに `firebase/firestore.rules` の全文を貼り付けて公開
5. **Storage** → 始める → **ルール** タブに `firebase/storage.rules` の全文を貼り付けて公開
6. プロジェクトの設定 → 全般 → 「アプリを追加」→ **Web アプリ（</>）** を登録し、表示される `firebaseConfig`（apiKey / authDomain / projectId / storageBucket / messagingSenderId / appId）を控える

### 2. config.js に接続情報を入れる

```js
globalThis.WAGAYA_CONFIG = {
  FIREBASE: {
    apiKey: "AIzaSy...",
    authDomain: "your-project.firebaseapp.com",
    projectId: "your-project",
    storageBucket: "your-project.appspot.com",
    messagingSenderId: "1234567890",
    appId: "1:1234567890:web:...",
  },
  FCM_VAPID_KEY: "", // サーバー発プッシュを使う場合のみ
};
```

※ サービスアカウント等の管理者用秘密鍵は絶対に書かないでください。

### 3. 公開する（どちらか）

**A. Firebase Hosting（推奨・同じプロジェクトで完結）**

1. PC に Firebase CLI を入れる（`npm install -g firebase-tools`）→ `firebase login`
2. このフォルダで `firebase use --add` でプロジェクトを選び、`firebase deploy`（Hosting + ルールが `firebase.json` の指定で一緒にデプロイされます）
3. 発行された `https://your-project.web.app` が公開URLになります

**B. Cloudflare Pages（従来通りでも可）**

1. [Cloudflare](https://dash.cloudflare.com) → **Workers & Pages → Create → Pages → Upload assets** で、このフォルダの中身一式をアップロード（`firebase.json` 等の余分なファイルが混ざっても動作に影響しません）
2. 発行された `https://xxxx.pages.dev` が公開URLになります

どちらの場合も、スマホで開いて「ホーム画面に追加」するとアプリのように使えます。

### 4. 公開前の必須テスト（2アカウント検証）

本番URLで必ず確認してください（**Firestore ルールは実プロジェクト未検証**のため、この確認が安全の要です）：

1. アカウントAで登録 → 冷蔵庫を作成 → フレンドコードを控える
2. 食材を1つ登録する（写真も1枚添付してみる）
3. アカウントB（別のメールアドレス）で登録 → コードで参加 → **同じ食材が見え、数量を変更できる**こと
4. アカウントBで別の冷蔵庫を作成し、食材を登録する
5. アカウントAに戻り、**Bの2つ目の冷蔵庫が見えない**こと（← これが最重要のセキュリティ確認）
6. 作成者がコードを再発行し、**旧コードで参加できない**こと
7. QRコードをスマホのカメラで読み取り、参加コードが自動で入ること
8. リアルタイム更新の確認：AとBで同じ冷蔵庫を開き、Bの変更がAの画面に自動で出ること
9. 退会の確認（2アカウント検証）：アカウントBで「退会する」を押し、**Bでログインできなくなる**こと、Aの冷蔵庫と在庫が残ること、Aが作った冷蔵庫でAが退会した場合は**Bへ作成者が引き継がれる**こと、同じメールアドレスで再登録できること（※ 退会直後は再認証を求められる場合があります。その場合は一度ログインし直してから退会をやり直してください）

## デモモードについて

`config.js` が空のまま開くとデモモードになります（画面上部に明示されます）。

- データはその端末のブラウザ内（localStorage）だけに保存され、外部送信されません
- 同じ端末内で複数アカウント・複数冷蔵庫を作り、ログアウト→別アカウントでコード参加、まで全フローが試せます
- デモのパスワード/コード照合もハッシュ化していますが、あくまで端末内の検証用です。本番の代替にはなりません

## 無料枠の注意

- Firebase Spark（無料）：Firestore は保存 1GiB・読み取り 5万回/日・書き込み 2万回/日まで。Authentication はメール/パスワード認証が無料枠で使えます。Storage は 5GB まで。Hosting は保存 10GB・転送 360MB/日まで
- **Supabase のような「1週間使われないと一時停止」はありません**。勝手に課金される構成にもなっていません（Blaze に上げない限りカード登録自体が不要）
- 利用者が大きく増えて無料枠を超えたら、その時点で Blaze（従量課金）への移行を検討してください
- Cloudflare Pages に置く場合の静的配信は従来通り無料・通信量無制限です

## 既知の制限・今後の課題

- 写真の AI 読み取り（旧 Muse 版にあった機能）は未実装です。写真は添付のみです
- **おつかい専用モード**（子ども向けに大きな文字とキャラだけで買い物を進める画面）は今後のアイデアです。現状は買い物リストの行でキャラ＋名前を大きく表示し、タップで知識ページに行ける形でおつかいを支援しています
- レシピの消費順は「どのロットから使うか」の提案・割り当て計画までで、「調理したので在庫を減らす」操作フローは未実装です（将来追加する場合は `planUsage` の順で減らす想定）
- サーバー発プッシュ通知は未有効化です（FCM のトークン登録と SW 受信のみ準備済み。ローカル通知のみ動作）。有効化手順は上記「プッシュ通知（サーバー発）について」を参照
- フレンドコード参加の試行回数制限は未実装です（Firestore ルールでは強制できないため。経緯と緩和策は「セキュリティ設計」参照）

- 本番モードの削除食材のゴミ箱はセッション内のみ（画面を閉じると復元できません）。デモモードのゴミ箱は端末内に残ります
- Firestore / Storage のセキュリティルールと FirebaseStore の実データ操作は、**実プロジェクトでは未検証**です（変換レイヤーの単体テストとデモモードの全フローは検証済み）。公開時は上記「2アカウント検証」を必ず実施してください
- プライバシーポリシー／利用規約はアプリ内ページとして組み込み済みです（本文は `js/legal.js`、元の下書きは `files/プライバシーポリシー・利用規約（案）.md`）。公開前に `LEGAL_INFO` の4つの空欄（運営者名・連絡先・公開URL・施行日）を記入してください（上記「法的ページの値の差し替え」参照）

## ロールバックについて（旧 Supabase 版）

旧バックエンドに戻す場合は、`config.js` の `FIREBASE` を空に戻し、代わりに旧設定（`SUPABASE_URL` / `SUPABASE_ANON_KEY` / `VAPID_PUBLIC_KEY`）を入れると `js/supabase-store.js` 経由で動きます。その場合の手順・SQL は `supabase/schema.sql` と git 履歴側の旧 README を参照してください。なおデータそのものは移行されません（Firestore と Postgres の間で自動移行はしません）。
